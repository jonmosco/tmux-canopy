# Canopy compared with tmux workspace and agent tools

*Research date: 2026-10-06. Based on first-party READMEs and documentation, not hands-on testing or performance benchmarks. “Not documented” is not proof that a feature cannot be implemented. Canopy observations refer to this repository at `2c088c9`.*

## Which products are actually comparable?

- **Closest tmux sidebar competitors:** [agenmux](https://github.com/snirt/agenmux/blob/master/README.md), [tmux-agent-sidebar](https://github.com/hiroppy/tmux-agent-sidebar/blob/main/README.md), and [opensessions](https://github.com/Ataraxy-Labs/opensessions/blob/main/README.md). All put agent state alongside tmux navigation, but differ substantially in detection and runtime model.
- **Complementary session picker:** [tmux-sessionx](https://github.com/omerxx/tmux-sessionx/blob/main/README.md). It optimizes an *on-demand* session/window search; it does not claim to be a continuously visible pane/agent monitor.
- **Broader environments:** [herdr](https://github.com/herdrdev/herdr/blob/master/README.md) runs its *own* multiplexer/server; [jmux](https://github.com/jarredkenny/jmux/blob/main/README.md) wraps real tmux with a custom UI and a development-workflow layer. Neither is a drop-in plugin for an existing tmux client.
- **Different meaning of “sidebar”:** [tmux-sidebar](https://github.com/tmux-plugins/tmux-sidebar/blob/master/README.md) shows a *filesystem directory tree*, not sessions/windows/panes.

## Where Canopy stands

**Strong position as a general-purpose, low-infrastructure tmux navigator.** Canopy combines a complete session/window/pane tree, native-object operations, a global quick switcher, process and buffer views, responsive dock/popup modes, and optional multi-provider agent monitoring. It does so within an existing tmux setup without a separately running server ([Canopy features](https://github.com/jonmosco/tmux-canopy/blob/main/README.md#features), [architecture](https://github.com/jonmosco/tmux-canopy/blob/main/README.md#how-it-works), [views](https://github.com/jonmosco/tmux-canopy/blob/main/docs/reference.md#views)). Compared to sessionx, Canopy provides a persistent workspace overview and pane-level state; sessionx is leaner for searching for/creating sessions from arbitrary directories and has explicit zoxide, tmuxinator, and Git-branch conveniences ([sessionx configuration and usage](https://github.com/omerxx/tmux-sessionx/blob/main/README.md)).

**Agenmux is the most direct contemporary overlap.** It too offers a navigable sessions/windows/panes sidebar, agent-only view, popup, mouse support, desktop notifications, and agent attention filtering. Its config-defined agents and screen/title-based detection require no hooks; this makes new agent support and initial setup easier, but its inferred blocked state is different from Canopy's *verified* lifecycle reports from installed adapters ([agenmux README](https://github.com/snirt/agenmux/blob/master/README.md), [usage](https://github.com/snirt/agenmux/blob/master/docs/usage.md), [custom agents](https://github.com/snirt/agenmux/blob/master/docs/custom-agents.md), [Canopy lifecycle](https://github.com/jonmosco/tmux-canopy/blob/main/docs/reference.md#agent-lifecycle-adapters)). Neither method is universally more accurate: unconfigured adapters in Canopy leave process-only/unknown state, whereas text left on-screen can yield misleading inferred state. Canopy's process-tree and tmux-buffer views and no-daemon model remain clear distinctions ([Canopy views](https://github.com/jonmosco/tmux-canopy/blob/main/docs/reference.md#views), [agenmux README](https://github.com/snirt/agenmux/blob/master/README.md)).

**Agent-first competitors go deeper on agent workflows.** tmux-agent-sidebar documents richer prompts, tool calls, progress, Git/activity views and one-step worktree/agent lifecycle, but concentrates on Claude Code, Codex and OpenCode ([README](https://github.com/hiroppy/tmux-agent-sidebar/blob/main/README.md)). opensessions adds per-thread unseen states, repository/port context and an HTTP API for custom status/progress/log events at the cost of an always-running server and watchers; its README says it is local-only ([README and caveats](https://github.com/Ataraxy-Labs/opensessions/blob/main/README.md)). Canopy prioritizes tmux objects and read-only monitoring rather than managing Git/worktrees or exposing an agent-control API ([Canopy actions](https://github.com/jonmosco/tmux-canopy/blob/main/docs/reference.md#native-object-actions), [architecture](https://github.com/jonmosco/tmux-canopy/blob/main/README.md#how-it-works)).

**Herdr and jmux solve a larger problem.** Herdr offers a cross-machine combined agent view and a native CLI/socket API, and owns the terminal runtime; its server can restore saved layout after restart but *not* resurrect the old processes ([herdr README](https://github.com/herdrdev/herdr/blob/master/README.md)). jmux keeps real tmux underneath but adds a custom outer interface, issue/code-host integrations, worktrees, diff review, and an agent-control CLI ([jmux README](https://github.com/jarredkenny/jmux/blob/main/README.md)). These are genuine feature gaps for Canopy, but adding them would change its “enhance existing tmux; no daemon” scope rather than simply catch up with a peer ([Canopy design](https://github.com/jonmosco/tmux-canopy/blob/main/README.md#how-it-works)).

## Product opportunities and constraints

1. **Keep the core positioning:** *a client-following tmux workspace tree with optional verified multi-agent awareness and no separate service*. That is more precise than claiming to be the most capable agent orchestrator ([Canopy architecture](https://github.com/jonmosco/tmux-canopy/blob/main/README.md#how-it-works); comparisons above).
2. **Consider opt-in project/worktree affordances**, starting with Git branch/worktree labels or a quick action. Sessionx explicitly supports Git branch labels and directory-backed session creation; tmux-agent-sidebar and jmux automate worktree creation ([sessionx README](https://github.com/omerxx/tmux-sessionx/blob/main/README.md), [tmux-agent-sidebar README](https://github.com/hiroppy/tmux-agent-sidebar/blob/main/README.md), [jmux README](https://github.com/jarredkenny/jmux/blob/main/README.md)). An on-demand action avoids silently adding a Git poller to Canopy.
3. **Evaluate user-configurable *detection* separately from verified *state*.** Agenmux offers custom agent definitions without code; Canopy currently documents a fixed set of agent kinds and adapter installers. Preserve an explicit distinction between process present, heuristic inference, and hook-confirmed state ([agenmux custom agents](https://github.com/snirt/agenmux/blob/master/docs/custom-agents.md), [Canopy agent monitoring](https://github.com/jonmosco/tmux-canopy/blob/main/docs/reference.md#agent-lifecycle-adapters)).
4. **Do not claim universal persistence or remote alerts.** Canopy documents limits for simultaneous sidebar owners, directory-only refresh, and SSH desktop alerts. Herdr's multi-machine view and jmux's workflow controls are different product categories, not small missing toggle options ([Canopy limitations](https://github.com/jonmosco/tmux-canopy/blob/main/README.md#current-limitations), [herdr README](https://github.com/herdrdev/herdr/blob/master/README.md), [jmux README](https://github.com/jarredkenny/jmux/blob/main/README.md)).

This is a feature/architecture comparison, **not** a claim about relative speed, correctness in use, popularity, or maintenance quality. Those need reproducible hands-on tests and comparable workloads.
